# مخطط Firebase والإعداد

المخطط الكامل وجدول الصلاحيات في [`GAME_FLOW.md §4`](../GAME_FLOW.md).
هذه الوثيقة تشرح **لماذا** بُني هكذا، وكيف تُشغّله.

## لماذا Realtime Database لا Firestore

اللعبة تنتقل بين المراحل بزمن استجابة يجب ألا يُلاحَظ حول طاولة واحدة، وتحتاج
`onDisconnect` لرصد الحضور. RTDB يقدّم الاثنين أصلًا. الجولة كلها أقل من 10KB،
فلا حاجة للاستعلامات المركّبة التي يتفوق بها Firestore.

## التشغيل

### 1. مشروع Firebase

1. أنشئ مشروعًا على <https://console.firebase.google.com>.
2. فعّل **Realtime Database**.
3. فعّل **Authentication → Anonymous**.

الخطة المجانية (Spark) تكفي النسخة الحالية بالكامل.

### 2. متغيرات البيئة

أنشئ `.env.local` في جذر المشروع:

```
VITE_FIREBASE_API_KEY=...
VITE_FIREBASE_AUTH_DOMAIN=...
VITE_FIREBASE_DATABASE_URL=https://<project>-default-rtdb.firebaseio.com
VITE_FIREBASE_PROJECT_ID=...
VITE_FIREBASE_APP_ID=...
```

بلا هذه المتغيرات يعمل المشروع تلقائيًا على **النقل المحلي** (تبويبات متعددة على
جهاز واحد)، وتظهر شارة «وضع محلي — بلا خادم» على الشاشة الرئيسية.
حزمة Firebase تُحمَّل ديناميكيًا، فلا يدفع ثمنها من لا يستخدمها.

### 3. نشر قواعد الأمان

```bash
firebase deploy --only database
```

بملف [`firebase/database.rules.json`](../firebase/database.rules.json).

**لا تشغّل جلسة حقيقية بقواعد الاختبار المفتوحة** — الأسرار كلها في قاعدة
البيانات، و`databaseURL` يُشحن داخل حزمة الويب فيقرؤه أي زائر. ابدأ بـ Locked
mode وانشر هذه القواعد قبل أول جلسة.

**لا تضع تعليقات داخل ملف القواعد.** فايربيس يعتبر كل مفتاح لا يبدأ بنقطة
(`.read`، `.write`، `.validate`، `.indexOn`) اسمَ مسار ابن، وقيمته يجب أن
تكون كائنًا `{}`. مفتاح مثل `"_comment": "شرح"` يُرفض بـ
`Error saving rules — Expected '{'`. الشرح مكانه هذا الملف.

## فخّ الشكل: ما يعود ليس ما كُتب

قاعدة Realtime **تحذف كل حقل قيمته `null`، وتحذف المصفوفة الفارغة كاملةً**.
فالسرّ الذي يُكتب هكذا:

```js
{ dice: [3,5], effectiveSlots: [], soloSlots: [], inspection: null, knownAllies: [] }
```

يعود من الشبكة هكذا:

```js
{ dice: [3,5] }
```

وقد كلّف هذا جولةً كاملة قبل أن يُكتشف:

- `secret.effectiveSlots.includes(slot)` ترمي `TypeError`، فتنهار شجرة العرض
  وتبقى شاشة اللاعب **فارغة** حتى يُحدِّث الصفحة — ومعها ينقطع حضوره فيظهر
  للطاولة كأنه خرج.
- `buildResults` تكتب `undefined`، فترفض القاعدة الصفحة كاملةً وتقف الجولة عند
  التصويت بعد وصول كل الأصوات، بلا رسالة واحدة.

**العلاج في مكان واحد:** `hydrateSecret` في `src/game/deal.ts`، تُطبَّق عند كل
قراءة في `firebaseTransport`. لا حرّاس `?.` متفرّقة في عشرين شاشة — حدٌّ واحد
يدخل منه كل شيء.

**وما يمنع تكرارها:** النقل المحلّي صار يحذف مثلها بالضبط (`stripLikeFirebase`
في `localTransport.ts`). كونه أكرم من الحقيقي — يمرّ عبر JSON فيحفظ كل شيء —
هو ما جعل العطل يمرّ من ١٤٦ اختبارًا ومن قيادة آلية لجولة كاملة. البروفة التي
لا تُخطئ كما يُخطئ العرض ليست بروفة.

## منطق القواعد

### مبدأ لا يُخترق: لاعب لا يقرأ سر لاعب آخر

لا يوجد `.read` على مستوى `rooms/$code`. لو وُضع لسرت الصلاحية إلى كل ما تحته،
لأن قواعد RTDB **تراكمية**: ما يُمنح عند الأب لا يمكن سحبه عند الابن.

لذلك تُمنح القراءة على كل مسار عام على حدة (`meta`, `settings`, `players`,
`round/progress`, `round/results`)، بينما `round/secrets/$uid` تُمنح لصاحبها وحده
(وللمضيف — انظر أدناه)، و `round/votes` للمضيف فقط.

### ما تمنعه القواعد صراحةً

| المحاولة | ما يوقفها |
|---|---|
| قراءة سر لاعب آخر | `.read` على `secrets/$uid` مقيّد بـ `auth.uid === $uid` |
| تغيير دوره | `role` يُشترط `newData.val() === data.val()` لغير المضيف |
| تغيير نرده بعد التأكيد | `dice` يُشترط `progress/$uid/diceAck !== true` |
| منح نفسه `soloSlots` أو حلفاء | `soloSlots` و `knownAllies` للمضيف فقط |
| التصويت مرتين | `!data.exists()` على `votes/$uid` |
| التصويت لنفسه | `newData.val() !== $uid` |
| التصويت للاعب وهمي | `players/{target}` يجب أن يكون موجودًا |
| قراءة أصوات غيره | `.read` على `votes` للمضيف فقط |
| تغيير المرحلة | `meta` يكتبه `hostUid` فقط |
| ادّعاء أنه المضيف | `isHost` يُشترط تطابقه مع `meta/hostUid` |
| اسم فارغ أو طويل | `name` بين 1 و24 حرفًا |
| مقعد خارج النطاق | `seat` بين 0 و7 |

### حدّ معروف: المضيف طرف موثوق

المضيف يقرأ `round/secrets` لأن ثلاث عمليات تحتاج أسرار **أكثر من لاعب**:

1. حساب الاستيقاظ المنفرد — يحتاج مواعيد الجميع.
2. تحويل المختارين إلى متعاونين — يكتب في أسرار لاعبين آخرين.
3. كشف موعد الجار عند الفحص — يقرأ سر الجار ويكتب في سر الفاحص.

جهاز اللاعب لا يملك أيًّا من هذه الصلاحيات، فالعزل **بين اللاعبين** كامل.
إزالة ثقة المضيف تتطلب Cloud Functions.

### مسار الترقية إلى Cloud Functions

كل المنطق المعني معزول في [`src/game/director.ts`](../src/game/director.ts) كدوال
تأخذ `RoomTransport` وتعيد نتائج، والمنطق الحاسم تحته دوال **نقية** في
`src/game/{deal,night,accomplice,vote}.ts` لا تعرف الشبكة إطلاقًا.

الترقية:

1. انقل `director.ts` والدوال النقية إلى `functions/`.
2. حوّل كل دالة إلى Callable Function.
3. غيّر `.write` على `secrets` إلى `false` للجميع (Admin SDK يتجاوز القواعد).
4. غيّر `.read` على `secrets` إلى `auth.uid === $uid` فقط.
5. استبدل استدعاءات `director` في `HostScreen.tsx` بـ `httpsCallable`.

الشاشات لا تتغير.

## الحجم والتكلفة

| البند | التقدير |
|---|---|
| حجم الغرفة | ‎6–10 KB لجلسة من 8 لاعبين |
| الكتابات في الجولة | ≈ 120 (أدوار، نرد، تأكيدات، مراحل، أصوات، نتائج) |
| الاتصالات المتزامنة | عدد اللاعبين + 1 |
| حد Spark | 100 اتصال متزامن، 1GB تخزين، 10GB/شهر |

تنظيف: الغرف لا تُحذف تلقائيًا في النسخة الحالية.
**مهمة مفتوحة** — أضف Scheduled Function تمسح الغرف الأقدم من 24 ساعة.
